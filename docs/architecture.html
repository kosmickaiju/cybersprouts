What's doing what, and where

Cybersprouts is a static mockup: four HTML pages, one stylesheet, four scripts, no build step and no server. Every behaviour in the product — gating, the placement test, the colour change when you pick a team — comes from three files. This page maps them.

orientation

The shape of it

There is no framework, no bundler and no package manager. Each page is plain HTML that loads data.js, then app.js, then one page-specific script. Those files don't import each other — they just declare top-level consts that land in the same global scope, so the order of the <script> tags is the dependency graph. Open any page with open index.html and it works.

The split that matters is content versus rules versus view. data.js is 1,115 lines of pure content and holds no logic. app.js is the only place that knows how progress is stored and which modules are unlocked. Each page script does one job: turn that state into DOM for one screen.

app.js · Store

All of the state

One localStorage key holds everything the app remembers. There is no account, no sync and no server — progress lives in whichever browser made it, and the footer's Reset progress link deletes the key outright. 

// localStorage['cybersprouts.v1']
{
  completed: [ "basics/cia-triad", "python/setup", ... ],  // "moduleId/lessonId"
  team:      'red' | 'yellow' | 'blue' | null,
  placement: {                                     // null until the test is applied
    correct: 21, of: 24,
    cleared: [ "basics", "python", "terminal" ],
    rechecked: [ "terminal" ],
    takenAt: "2026-09-10T…"
  }
}

completed is the single source of truth. Everything else — a module's status, the percentage in the header, whether the fork is open — is derived from it on each render by the four helpers in app.js: moduleProgress(), moduleStatus(), branchesUnlocked() and overallProgress(). Nothing is cached.

app.js · moduleStatus()

What unlocks what

moduleStatus() returns one of four strings, and every card on the roadmap is styled from it:

StatusMeaningCard behaviour
doneEvery lesson in the module is in completed.Green tick styling, still clickable.
currentThe next thing to do: the first core module with unfinished prerequisites cleared, or the chosen branch's first unfinished module."Up next" label, accent ring.
openReachable but not the highlighted next step — the two branches you didn't pick, and any untouched anytime module.Normal card, quiet.
lockedPrerequisites unmet.Rendered as a <div>, not an <a> — there is no link to follow.

The percentage moves when you pick a team

overallProgress() counts the core spine, the three anytime modules, and — only once chosen — your specialization. So the denominator in the header pill changes:

No team selected: 65 lessons (49 core + 16 anytime). Red or yellow: 80. Blue: 90. Picking a team therefore makes your percentage drop, because the numerator doesn't change. Worth deciding whether that's the behaviour you want.

placement.js

How the placement test writes progress

The fork is never skippable: PLACEMENT_QUESTIONS covers the eight core modules only, so the best possible result is landing at the fork with a specialization to choose. RECHECK_QUESTIONS is a second, separate bank — three fresh questions per core module, never shown in the main run.

app.js · applyTheme() + styles.css

The colour change

One function and one attribute. applyTheme(team) sets data-team on <html>; the stylesheet has three blocks that redefine the accent and neutral tokens, and every component reads those tokens rather than literal colours. That's why the whole interface changes with one attribute write. 

/* styles.css — the base tokens… */
:root { --accent: #57d68f; --bg: #0b0e0d; --surface: #141918; … }

/* …and the three swaps. Note the neutrals shift too, not just the accent. */
[data-team='red']    { --accent: #ff6b6b; --bg: #0d0a0a; … }
[data-team='yellow'] { --accent: #f0c04a; --bg: #0d0b06; … }
[data-team='blue']   { --accent: #63a4ff; --bg: #090b10; … }

lesson.js adds one wrinkle worth knowing: opening any branch lesson themes the page for that branch, whatever your saved team is, and without overwriting it. So a blue-team learner who peeks at a red-team lesson sees red for that page and blue again everywhere else. --red, --yellow, --blue and --ai stay fixed at all times, so branch labels keep their own identity inside any theme.

roadmap.js + roadmap.html

How cards land on the vine

The vine is a hand-drawn SVG in a 1200 × 2860 coordinate space, growing bottom-up from the seed at (600, 2800) to the fork at (600, 1100), where three stems fan out to x = 210 / 600 / 990. The module cards are not in the SVG — they're absolutely-positioned HTML in an overlay div. roadmap.js converts each module's pos into a percentage of that same canvas, so the two layers stay aligned at any width.

That maintenance cost is already visible in the branch spacing: red and yellow carry three modules over the same stem height at 420 units apart, while blue packs five in at 210 apart. The stems are the same length; only the density differs.

worth knowing

Sharp edges

Things that are true of the code today and easy to trip over later. None of these are bugs right now — they're the places where the mockup's shortcuts will bite as it grows.

  1. One global namespace, no guardrails Every top-level const across all four scripts shares one scope. roadmap.js, lesson.js and placement.js each define their own render() — harmless only because no page loads two of them. A duplicate name across data.js and app.js would throw on load.
  2. data.js defines itself, then extends itself LESSON_BODIES and RECHECK_QUESTIONS get a second helping via Object.assign (lines 541 and 1028), and PLACEMENT_QUESTIONS via .push() (line 931). Reading only the first declaration shows you half the data.
  3. A written lesson is recorded in three places The body goes in LESSON_BODIES, the lesson gets showcase: true in CURRICULUM, and its title is hard-coded into the "look for these" prose inside lesson.js's draftBody(). All three are in sync at 10 lessons — by hand. Nothing reads showcase; it's documentation.
  4. Anytime modules aren't on the vine at all roadmap.js filters on m.pos, and the three free modules don't have one. They're reachable from the header nav, the roadmap sidebar panel, and the narrow-screen list — but a learner scanning the vine won't see them.
  5. Progress is per-browser and unversioned Store.read() merges the stored object over blank(), so new fields get defaults — but there's no migration path if the shape of completed ever changes. The key name carries the only version marker: .v1.
  6. The header renders before the page script runs initChrome() paints the lesson count at load; anything that changes progress mid-page has to call renderHeader() again. roadmap.js does this after a team switch — a new page that mutates state will need to remember it too.
