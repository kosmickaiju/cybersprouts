cybersprouts · repository map

What's doing what, and where

Cybersprouts is a static mockup: five HTML pages, one stylesheet, eight scripts and no build step. Every behaviour in the product — gating, the placement test, the colour change when you pick a team — comes from three files. A fourth concern, accounts, sits alongside them and can be switched off entirely. This page maps them.

orientation

The shape of it

There is no framework, no bundler and no package manager. Each page is plain HTML that loads data.js, the three account scripts, then app.js, then one page-specific script. Those files don't import each other — they just declare top-level consts that land in the same global scope, so the order of the <script> tags is the dependency graph.

The split that matters is content versus rules versus view. data.js is 1,115 lines of pure content and holds no logic. app.js is the only place that knows how progress is stored and which modules are unlocked. Each page script does one job: turn that state into DOM for one screen.

Accounts are a fourth layer, deliberately bolted on the side rather than threaded through. supabase-config.js, auth.js and sync.js are the only files that know a server exists, and if supabase-config.js still holds its placeholder values, all three go dormant and the platform behaves exactly as it did when it was local-only. That is the state the repository ships in. Nothing else in the codebase branches on whether someone is signed in — Store is still read synchronously from localStorage on every render, and it never waits on a network.

app.js · Store

All of the state

One localStorage key holds everything the app remembers, and it is always the working copy — every read is synchronous, and nothing on a render path waits on a network. When a learner is signed in, sync.js mirrors this same document to the progress table column for column; when they are not, it is the only copy there is. 

// localStorage['cybersprouts.v1']
{
  completed: [ "basics/cia-triad", "python/setup", ... ],  // "moduleId/lessonId"
  team:      'red' | 'yellow' | 'blue' | null,
  placement: {                                     // null until the test is applied
    correct: 21, of: 24,
    cleared: [ "basics", "python", "terminal" ],
    rechecked: [ "terminal" ],
    takenAt: "2026-09-10T…"
  },

  // ── added for sync. Not read by any rendering code; they exist
  //    only so a merge can tell which side of a conflict is newer.
  teamUpdatedAt: "2026-09-14T…" | null,   // stamped only when team changes
  updatedAt:     "2026-09-17T…" | null
}

completed is the single source of truth. Everything else — a module's status, the percentage in the header, whether the fork is open — is derived from it on each render by the four helpers in app.js: moduleProgress(), moduleStatus(), branchesUnlocked() and overallProgress(). Nothing is cached.

auth.js + sync.js · docs/schema.sql

Accounts, and what happens to progress

The whole point of an account here is that progress stops being a property of a browser. The risk that comes with it is the one every sync feature has: a learner who finishes three modules, makes an account, and finds an empty roadmap does not come back. So the interesting part is not sign-in — it is the merge.

MomentRuleWhy that one
pull Union of completed Additive only. Two devices used on different days both keep their work.
push Local document wins outright A union here would make un-completing a lesson impossible — the removal would come straight back on the next pull.
sign-in Union, then push The one moment anonymous progress can be lost. This is the step that rescues it.
sign-out Clear the local copy Not only privacy on a shared machine: leftover progress would otherwise be unioned into the next account signed in on this browser.

The security model is four policies, not the key

The anon key sits in supabase-config.js in plain sight, and that is how it is meant to work — it identifies the project, it does not authorize anything. What actually separates one learner's row from another's is Row Level Security in docs/schema.sql: four policies scoped to authenticated, each matching auth.uid() = user_id. Insert and update carry a with check clause as well as using, which is what stops someone writing a row stamped with a user id that isn't theirs.

Two consequences worth holding onto. First, if RLS is ever disabled on that table, every learner's row becomes readable by anyone who views the page source — the key was never the protection. Second, the client is untrusted code running on someone else's computer, so the integrity rules (team must be one of three values, completed must be an array, capped at 2,000 entries) are check constraints in Postgres rather than validation in JavaScript.

The service_role key must never appear in this repository. It bypasses RLS entirely, which is also why account deletion isn't in the UI yet — doing it properly needs an Edge Function rather than client-side code.

The percentage moves when you pick a team

overallProgress() counts the core spine, the three anytime modules, and — only once chosen — your specialization. So the denominator in the header pill changes:

No team selected: 65 lessons (49 core + 16 anytime). Red or yellow: 80. Blue: 90. Picking a team therefore makes your percentage drop, because the numerator doesn't change. Worth deciding whether that's the behaviour you want.

placement.js

How the placement test writes progress

The fork is never skippable: PLACEMENT_QUESTIONS covers the eight core modules only, so the best possible result is landing at the fork with a specialization to choose. RECHECK_QUESTIONS is a second, separate bank — three fresh questions per core module, never shown in the main run.

app.js · applyTheme() + styles.css

The colour change

One function and one attribute. applyTheme(team) sets data-team on <html>; the stylesheet has three blocks that redefine the accent and neutral tokens, and every component reads those tokens rather than literal colours. That's why the whole interface changes with one attribute write. 

/* styles.css — the base tokens… */
:root { --accent: #57d68f; --bg: #0b0e0d; --surface: #141918; … }

/* …and the three swaps. Note the neutrals shift too, not just the accent. */
[data-team='red']    { --accent: #ff6b6b; --bg: #0d0a0a; … }
[data-team='yellow'] { --accent: #f0c04a; --bg: #0d0b06; … }
[data-team='blue']   { --accent: #63a4ff; --bg: #090b10; … }

lesson.js adds one wrinkle worth knowing: opening any branch lesson themes the page for that branch, whatever your saved team is, and without overwriting it. So a blue-team learner who peeks at a red-team lesson sees red for that page and blue again everywhere else. --red, --yellow, --blue and --ai stay fixed at all times, so branch labels keep their own identity inside any theme.

roadmap.js + roadmap.html

How cards land on the vine

The vine is a hand-drawn SVG in a 1200 × 2860 coordinate space, growing bottom-up from the seed at (600, 2800) to the fork at (600, 1100), where three stems fan out to x = 210 / 600 / 990. The module cards are not in the SVG — they're absolutely-positioned HTML in an overlay div. roadmap.js converts each module's pos into a percentage of that same canvas, so the two layers stay aligned at any width.

That maintenance cost is already visible in the branch spacing: red and yellow carry three modules over the same stem height at 420 units apart, while blue packs five in at 210 apart. The stems are the same length; only the density differs.

worth knowing

Sharp edges

Things that are true of the code today and easy to trip over later. None of these are bugs right now — they're the places where the mockup's shortcuts will bite as it grows.

  1. One global namespace, no guardrails Every top-level const across all eight scripts shares one scope. roadmap.js, lesson.js, placement.js and account.js each define their own render(), and placement.js and account.js both define root — harmless only because no page loads two of them. A duplicate name across the shared scripts would throw on load.
  2. data.js defines itself, then extends itself LESSON_BODIES and RECHECK_QUESTIONS get a second helping via Object.assign (lines 541 and 1028), and PLACEMENT_QUESTIONS via .push() (line 931). Reading only the first declaration shows you half the data.
  3. A written lesson is recorded in three places The body goes in LESSON_BODIES, the lesson gets showcase: true in CURRICULUM, and its title is hard-coded into the "look for these" prose inside lesson.js's draftBody(). All three are in sync at 10 lessons — by hand. Nothing reads showcase; it's documentation.
  4. Anytime modules aren't on the vine at all roadmap.js filters on m.pos, and the three free modules don't have one. They're reachable from the header nav, the roadmap sidebar panel, and the narrow-screen list — but a learner scanning the vine won't see them.
  5. Progress is unversioned Store.read() merges the stored object over blank(), so new fields get defaults — which is exactly how updatedAt and teamUpdatedAt were added without breaking anyone's saved state. There's still no migration path if the shape of completed itself ever changes, and now that the same document also lives in Postgres, a shape change has two places to land. The key name carries the only version marker: .v1.
  6. Simultaneous devices resolve last-write-wins Pulls union, but pushes overwrite. Two browsers open at the same minute can therefore lose an un-completion — mark a lesson done on the laptop, undo it on the phone, and the laptop's next push can put it back. Fixing this properly needs per-lesson tombstones rather than a plain array, which is not worth the complexity for progress that only ever grows. Sequential use across devices, which is the real pattern, is unaffected.
  7. A sync can change the page underneath the learner sync.js fires cybersprouts:progress after a pull; roadmap.js and lesson.js listen and redraw. placement.js deliberately does not — redrawing mid-question would be hostile — so a pull that lands during the test is only reflected once the results are applied. Any new page that renders progress needs to subscribe, or it will quietly show stale state.
  8. Auth resolves after first paint Auth.ready() is false until Supabase has checked the stored session, so the header reserves the account chip's footprint rather than rendering "Sign in" at someone who is already signed in. Anything new that branches on Auth.signedIn() has to handle the not-yet-known state too — treating it as "signed out" produces a visible flicker on every page load.
  9. Email delivery is the first thing that will break at scale Supabase's built-in sender is rate-limited to a handful of messages an hour. It is fine for testing and will silently stop new learners from confirming their accounts the moment there is real traffic. Connecting real SMTP is step 3 of docs/SETUP-ACCOUNTS.md and is a launch blocker, not a nice-to-have.
  10. The header renders before the page script runs initChrome() paints the lesson count at load; anything that changes progress mid-page has to call renderHeader() again. roadmap.js does this after a team switch — a new page that mutates state will need to remember it too.
